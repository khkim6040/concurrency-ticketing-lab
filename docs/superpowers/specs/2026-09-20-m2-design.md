# M2 설계 — 중복 배정

2026-09-20. 상위 스펙: `concurrency-ticketing-lab_spec.md`. M1 설계: `2026-09-20-m1-design.md`. 결정 근거: `docs/decisions.md`.

## 목표

좌석 단위 예약(`reservation` 테이블)을 넣고, 유니크 인덱스를 실행 시작 시 켜고 끄며, `doubleBookedSeats` 지표와 빨강 셀을 추가한다.

DoD: 유니크 제약 OFF에서 중복 배정이 재현되고, ON에서 0건이면서 `DuplicateKeyException` 카운트가 UI에 노출될 것.

## 범위 밖

`seat` 테이블(`status` 컬럼), `seatPickStrategy`(`hotspot`), 보조 인덱스, `errorBreakdown`의 나머지 항목, SSE, Redis, 비교·replay, 해설 패널.

`seat` 테이블을 빼는 이유: 중복 배정 지표는 `reservation`을 `seat_no`로 묶어 세면 나오고, `seat.status`를 두면 lost update가 생기는 두 번째 장소가 되어 오버셀 실험과 섞인다. `hotspot`을 빼는 이유: N=100, M=1,000이면 균등 랜덤만으로 좌석당 평균 10명이 몰려 20ms 창에서 확실히 재현된다. 둘 다 필요해지면 그때 추가한다.

## 핵심 결정: 좌석 먼저, 카운터 나중

한 요청은 **좌석 단계**(`reservation` INSERT, `doubleBooking` 전략)와 **카운터 단계**(`event.remaining` 차감, `oversell` 전략)를 이 순서로 거친다. 좌석을 잡은 요청만 카운터를 차감하고, 카운터가 SOLD_OUT이면 자기 행을 DELETE로 되돌린다.

- 유니크 위반은 카운터를 건드리기 전에 끝나므로 보상이 없다.
- `oversell`은 카운터만, `doubleBooking`은 좌석만 건드린다. `LOCAL_LOCK`의 `synchronized`와 `PESSIMISTIC`의 트랜잭션은 지금처럼 카운터 단계만 감싸므로 5×2=10 조합이 모두 곱으로 설명된다. 앱 1대 `LOCAL_LOCK` + 좌석 `NONE`에서도 중복 배정은 그대로 재현된다.
- 카운터를 먼저 두면 유니크 위반 시 `remaining + 1` 환불이 필요하고, 그 환불이 `LOCAL_LOCK`의 절대값 쓰기와 경합해 앱 1대에서도 원장이 깨진다. 환불을 락 안으로 넣으면 좌석 검사까지 직렬화되어 중복 배정이 사라지고 두 축이 직교하지 않게 된다.

기대 결과:

| oversell | doubleBooking | 기대 |
| --- | --- | --- |
| `CONDITIONAL_UPDATE` | `NONE` | ok=100, ledger 0, **doubleBookedSeats > 0** → FAIL. "총량은 맞는데 좌석이 겹친다" |
| `CONDITIONAL_UPDATE` | `UNIQUE_CONSTRAINT` | doubleBookedSeats 0, duplicateKeyCount ≈ 900 → PASS |
| `NONE` | `NONE` | oversold 900 + 중복 좌석 다수 → FAIL |
| `NONE` | `UNIQUE_CONSTRAINT` | 좌석 100개만 통과하므로 oversold 0, 그러나 카운터는 깨져 ledgerMismatch ≈ -99 → FAIL. 유니크 제약은 마지막 계층이고, ledgerMismatch는 최종 검증 장치 |

## 스키마 (`db/schema.sql`)

```sql
CREATE TABLE IF NOT EXISTS reservation (
    id       BIGINT PRIMARY KEY AUTO_INCREMENT,
    event_id BIGINT NOT NULL,
    seat_no  INT    NOT NULL,
    user_id  BIGINT NOT NULL
);
```

유니크 인덱스 `ux_reservation_seat (event_id, seat_no)`는 스키마에 넣지 않고 web이 실행 시작 시 토글한다. `created_at`은 쓰는 곳이 없어 뺀다. 행이 실행당 1,000개 이하라 보조 인덱스 없이 풀 스캔으로 충분하다.

## 타입 (`Models.kt`)

- `enum class DoubleBookingStrategy { NONE, UNIQUE_CONSTRAINT }`
- `StrategySet(oversell, doubleBooking = DoubleBookingStrategy.NONE)`. 기본값이 NONE이라 기존 요청 본문과 `dod.sh`가 그대로 동작한다.
- `Outcome`에 `SEAT_TAKEN`(앱 조회로 거절), `DUPLICATE_KEY`(DB가 거절) 추가. 플래그 대신 값 두 개로 나누면 `duplicateKeyCount = count(DUPLICATE_KEY)` 한 줄이다.
- `ReserveRequest`에 `seatNo: Int`, `doubleBooking: DoubleBookingStrategy` 추가. `ReserveResponse`는 그대로. web이 보낸 좌석을 이미 알고 있어 되돌려 받을 필요가 없다.
- `Progress(seatCount)`에 `seats: List<AtomicInteger>` 추가. Jackson이 숫자 배열로 직렬화한다.
- `ConsistencyMetrics`에 `doubleBookedSeats: Int`, `PerformanceMetrics`에 `duplicateKeyCount: Int` 추가.

## 앱 흐름 (`app/ReservationService.reserve`)

1. 좌석 단계
   - `NONE`: `SELECT COUNT(*) FROM reservation WHERE event_id=? AND seat_no=?` → 1 이상이면 `SEAT_TAKEN` → `Thread.sleep(raceWindowMs)` → `INSERT`. M1과 같은 원칙으로 read-modify-write 창 사이에서 잠든다.
   - `UNIQUE_CONSTRAINT`: 바로 `INSERT`. `DuplicateKeyException`을 잡아 `DUPLICATE_KEY`. 조회도 sleep도 없다(`CONDITIONAL_UPDATE`와 같은 이유).
2. 카운터 단계: 기존 `when (strategy)` 그대로.
3. 결과가 OK가 아니면 `DELETE FROM reservation WHERE event_id=? AND seat_no=? AND user_id=?`로 자기 행만 되돌린다. `user_id`가 실행 내 유일하므로 키 홀더가 필요 없다.

`ReserveController`는 바뀌지 않는다.

## 웹 흐름 (`web/LoadRunner.run`)

- 실행 시작 시 `TRUNCATE TABLE reservation` 후 `information_schema.STATISTICS`에서 `ux_reservation_seat` 유무를 확인해 원하는 상태와 다르면 `CREATE UNIQUE INDEX` / `DROP INDEX`. TRUNCATE가 필요한 이유는 이전 `NONE` 실행의 중복 행이 남아 있으면 유니크 인덱스 생성 자체가 실패하기 때문이다. 동시 실행이 1건이라 DDL 경합은 없다. 이전 실행 리포트는 web 메모리에 있으므로 행을 지워도 잃는 것이 없다.
- 좌석 선택: `Random(spec.seed)`로 `IntArray(userCount) { nextInt(seatCount) + 1 }`을 미리 만들어 user별로 쓴다. 지금까지 쓰이지 않던 `seed`가 처음으로 결과를 결정한다.
- 응답이 OK이면 `progress.seats[seatNo - 1]`을 증가시킨다.
- 실행 후 `SELECT COUNT(*) FROM (SELECT seat_no FROM reservation WHERE event_id=? GROUP BY seat_no HAVING COUNT(*) > 1) t`로 `doubleBookedSeats`를 DB에서 직접 센다.
- DEGRADED 기준선 키에 `doubleBooking`을 추가한다. 좌석 `NONE` 경로가 sleep을 하나 더 하므로 같은 좌석 전략끼리만 비교해야 한다.

기본값(`doubleBooking=NONE`)에서도 모든 요청이 조회 + sleep + INSERT를 추가로 거치므로 README의 M1 처리량 수치가 다소 바뀐다. 락 밖에서 병렬로 잠드는 것이라 `CONDITIONAL_UPDATE`는 10% 안팎, 직렬화 전략은 거의 영향이 없을 것으로 본다. 표는 M2 결과와 함께 다시 측정해 갱신한다.

## 지표와 판정 (`buildReport`)

- `buildReport(..., doubleBookedSeats)` 파라미터 추가.
- `duplicateKeyCount = samples.count { it.outcome == DUPLICATE_KEY }`.
- `oversoldCount`, `ledgerMismatch` 계산은 그대로. `SEAT_TAKEN`·`DUPLICATE_KEY`는 OK가 아니므로 자연히 빠진다.
- 정합 = `oversoldCount == 0 && ledgerMismatch == 0 && doubleBookedSeats == 0`. DEGRADED 규칙은 M1 그대로.

## UI (`static/index.html`)

- `doubleBooking` 라디오 그룹(NONE 기본 / UNIQUE_CONSTRAINT) 추가. 요청 본문 `strategies.doubleBooking`.
- 그리드가 실제 좌석이 된다. 칸 i는 `progress.seats[i]`가 0이면 회색, 1이면 초록, 2 이상이면 빨강. `ok > N`인 초과분은 M1처럼 주황 칸을 뒤에 붙인다.
- 리포트는 JSON 그대로. `doubleBookedSeats`와 `duplicateKeyCount`가 거기에 나온다. 강조 문구는 M4 해설 패널 몫이다.

## 검증

- `ReportTest`: 중복 좌석이 있으면 FAIL, `duplicateKeyCount` 합산. 기존 7개 유지.
- `scripts/dod.sh`: 기존 M1 행렬(좌석 전략 NONE)은 유지하고 M2 구간을 추가한다. `CONDITIONAL_UPDATE`, 앱 2대, N=100, M=1,000, 20ms에서 좌석 `NONE`과 `UNIQUE_CONSTRAINT`를 각 10회. 출력에 `dup=`(doubleBookedSeats)와 `dupKey=`(duplicateKeyCount) 컬럼 추가. 기대: `NONE`은 oversold 0·ledger 0인데 dup > 0으로 10/10 FAIL, `UNIQUE_CONSTRAINT`는 dup 0·dupKey ≈ 900으로 10/10 PASS.
- 실행 후 README에 M2 표와 로드맵 체크, `decisions.md`에 결정 추가(좌석 먼저, `seat` 테이블·`hotspot` 보류, TRUNCATE + DDL 토글, 보조 인덱스 없음, `SEAT_TAKEN`/`DUPLICATE_KEY` 분리).
