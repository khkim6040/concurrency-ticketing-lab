# M3 설계 — 캐시 계층

2026-09-20. 상위 스펙: `concurrency-ticketing-lab_spec.md`. M2 설계: `2026-09-20-m2-design.md`. 결정 근거: `docs/decisions.md`.

## 목표

Redis 잔여석 캐시와 조회 경로를 넣고, 캐시 전략 4종(`NONE` / `TTL_SHORT` / `INVALIDATE_ON_WRITE` / `REDIS_AS_SOT`)을 실행 파라미터로 고르며, `phantomStockViews` 지표를 측정한다.

DoD: 모든 전략에서 stale 노출이 0이 되지 않는다는 점을 UI가 명시적으로 설명할 것. 최종 일관성 개념을 여기서 전달한다.

## 범위 밖

Redis 장애 시나리오, DB 비동기 쓰기(write-behind 큐), 조회자 수·주기 파라미터, 캐시 스탬피드, 분산 락, 접이식 해설 패널(M4), 비교·공유 링크(M4).

## 왜 어떤 전략도 stale을 0으로 만들지 못하는가

조회자가 잔여석을 폴링하고, 100번째 `OK` 응답이 web에 닿은 시각을 `soldOutAt`으로 잡는다. 그 뒤에 `remaining > 0`을 응답한 조회가 phantom이다.

- `NONE`: 첫 조회가 DB 값을 60초 TTL로 적재한다. 실행이 그보다 짧으면 매진 뒤에도 끝까지 옛값이다.
- `TTL_SHORT`: TTL 1초. 창이 TTL 이하로 줄지만 닫히지 않는다. 창을 닫는 TTL은 0, 즉 캐시를 없앤 것과 같다.
- `INVALIDATE_ON_WRITE`: 쓰기마다 `DEL`. 그러나 캐시 미스로 DB를 읽고 잠든 조회자가 마지막 쓰기의 `DEL` 뒤에 옛값을 `SET`하면, 더 이상 쓰기가 없어 다시 지워질 기회가 없다. 옛값이 TTL 60초까지 남는다. 스펙의 "삭제-재적재 경합은 잔존"이 이것이다. `raceWindowMs`는 재현율을 높일 뿐 경합을 만든 것이 아니다.
- `REDIS_AS_SOT`: 두 번째 복사본이 없으므로 위 셋의 문제가 사라진다. 남는 것은 전송 지연뿐이다. 매진 직전에 읽은 1이 매진 응답보다 늦게 web에 닿을 수 있다. 밀리초 미만이라 측정값은 0일 수 있고, 그래서 DoD가 "지표가 0이 아닐 것"이 아니라 "UI가 설명할 것"이다.

앞의 셋은 캐시 설계의 창이라 측정으로 재현되고, 넷째는 분산 시스템의 창이라 원리상 0이 아니지만 측정값은 0일 수 있다. 리포트는 측정값을 그대로 보이고 해설이 나머지를 말한다.

## 핵심 결정

### `REDIS_AS_SOT`는 oversell 축을 덮는다

`REDIS_AS_SOT`를 고르면 카운터 단계가 `DECR stock:{eventId}`로 바뀐다. 음수면 `INCR`로 되돌리고 `SOLD_OUT`, 아니면 DB에 `UPDATE event SET remaining = remaining - 1`을 동기로 쓰고 `OK`. `oversell` 전략은 무시되며 UI가 라디오를 비활성화해 그 사실을 보인다. "SoT가 Redis로 옮겨가면 DB 락 전략은 의미가 없다"가 교훈이다. `DECR`은 원자 연산이라 read-modify-write가 아니므로 `CONDITIONAL_UPDATE`처럼 sleep이 없다. 스펙의 "DB는 비동기"는 관측 가치가 없어 동기로 둔다.

대안이었던 write-through(DB가 결정하고 성공 후 Redis `DECR`)는 oversell 축과 완전히 직교하지만 "Redis가 SoT"인 시나리오가 사라지고 DB 커밋과 `DECR` 사이 창이 남는다. 스펙 충실도와 "stale이 0에 가까워지는 유일한 길은 저장소를 하나로 만드는 것"이라는 메시지를 위해 A를 택한다.

### `phantomStockViews`는 판정에 들어가지 않는다

`verdict`는 M2 규칙(oversold·ledger·doubleBooked) 그대로다. 어떤 전략도 0이 안 되는 지표를 FAIL 조건에 넣으면 M3부터 모든 실행이 FAIL이 된다. 학습 목표 4("stale read는 버그가 아니라 설계 선택")와 맞춰 리포트에 별도 표시하고 고정 해설을 붙인다.

### 조회 부하는 전용 조회자 상수

조회자 2개(앱 인스턴스마다 하나)가 10ms 간격으로 `GET /api/stock`을 폴링하고, 예매가 모두 끝난 뒤 2초 더 돈다. 꼬리 2초는 `TTL_SHORT`의 1초 만료가 창 안에 잡히게 한다. 예매 사용자가 예매 직전에 조회하는 모델은 조회가 출발선에 몰려 매진 이후 조회가 없으므로 부적합하다. `viewerCount`·`viewIntervalMs` 파라미터는 필요해지면 그때 연다.

## 타입 (`Models.kt`)

- `enum class CacheStrategy { NONE, TTL_SHORT, INVALIDATE_ON_WRITE, REDIS_AS_SOT }`
- `StrategySet(oversell, doubleBooking = NONE, cacheConsistency = CacheStrategy.NONE)`. 기본값이 있어 기존 요청 본문과 `dod.sh`가 그대로 동작한다.
- `ReserveRequest`에 `cache: CacheStrategy` 추가.
- `data class StockResponse(val remaining: Int, val fromDb: Boolean)`.
- `data class View(val sentAtMs: Long, val remaining: Int, val fromDb: Boolean)`. `sentAtMs`는 실행 시작 기준 상대 ms.
- `Progress`에 `lastView = AtomicInteger(-1)` 추가. 조회자가 마지막으로 본 값. -1은 아직 없음.
- `ConsistencyMetrics`에 `phantomStockViews: Int`, `staleWindowMs: Long` 추가.
- `PerformanceMetrics`에 `viewCount: Int`, `viewDbReads: Int` 추가.
- `buildReport(..., views: List<View> = emptyList(), soldOutAtMs: Long? = null)` 파라미터 추가.

## 앱 흐름

### 조회 경로 `GET /api/stock?eventId&cache&raceWindowMs`

새 클래스 `app/StockCache.kt`가 `StringRedisTemplate`로 키 `stock:{eventId}`를 다룬다. 매핑은 `ReserveController`에 한 줄 추가한다.

- `NONE` / `TTL_SHORT` / `INVALIDATE_ON_WRITE`: cache-aside. `GET` 히트면 그 값(`fromDb=false`). 미스면 DB `SELECT remaining FROM event WHERE id = ?` → `Thread.sleep(raceWindowMs)` → `SET stock:{eventId} value EX ttl` → `fromDb=true`. TTL은 `TTL_SHORT`가 1초, 나머지 둘이 60초. 지연을 읽기와 쓰기 사이에 두는 것은 다른 축과 같은 원칙이고, 이것이 `INVALIDATE_ON_WRITE`의 삭제-재적재 경합을 재현시킨다.
- `REDIS_AS_SOT`: `GET`만. 키가 없으면(정상 흐름에서는 없을 수 없다) DB를 읽고 `fromDb=true`로 응답한다.

### 예매 경로 `ReservationService.reserve`

좌석 단계와 좌석 되돌리기는 M2 그대로다. 카운터 단계만 바뀐다.

- `cache == REDIS_AS_SOT`: `when(strategy)` 대신 `StockCache.decrement(eventId)`. `DECR` 결과가 음수면 `INCR` 후 `SOLD_OUT`, 아니면 `UPDATE event SET remaining = remaining - 1 WHERE id = ?` 후 `OK`. `retries`·`activeConnections`는 기존과 같이 채운다.
- 나머지 셋: 기존 `when(strategy)`를 그대로 실행하고, 결과가 `OK`이면서 `cache == INVALIDATE_ON_WRITE`일 때만 `DEL stock:{eventId}`. `PESSIMISTIC`의 `tx.execute`가 반환된 뒤, 즉 커밋 이후에 지운다. 커밋 전에 지우면 조회자가 커밋 전 값을 재적재하는 별개의 버그가 된다.

## 웹 흐름 (`web/LoadRunner.run`)

- 이벤트 INSERT 직후 `cacheConsistency == REDIS_AS_SOT`이면 `SET stock:{eventId} N`. 다른 전략은 eventId가 실행마다 새로 나와 키가 처음부터 비어 있으므로 아무것도 하지 않는다.
- DEGRADED 기준선 키에 `cacheConsistency` 추가. `INVALIDATE_ON_WRITE`는 쓰기마다 `DEL`이 붙고 `REDIS_AS_SOT`는 경로가 다르므로 같은 캐시 전략끼리만 비교한다.
- 조회자: 가상 스레드 2개가 예매 스레드와 같은 `CountDownLatch`를 기다렸다가 출발한다. 조회자 i는 `targets[i % targets.size]`를 친다. 루프는 보낸 시각 기록 → `GET /api/stock` → `View`를 `ConcurrentLinkedQueue`에 추가 → `progress.lastView` 갱신 → `Thread.sleep(10)`. 실패한 조회는 warn 로그만 남기고 버린다.
- 종료: 예매 `futures`가 모두 끝난 뒤 `Thread.sleep(2000)` → `stop` 플래그 → 조회자 join. `throughput`의 분모(`elapsedMs`)는 예매 구간만 재므로 M2 수치와 비교 가능하다.
- `soldOutAtMs`: 예매 응답 처리에서 `progress.ok.incrementAndGet() == spec.seatCount`가 되는 순간의 상대 시각을 한 번 저장한다. DB가 실제로 0이 된 시점보다 약간 늦으므로 phantom을 적게 세는 쪽으로 보수적이다. `ok`가 N에 못 미치면 `null`.
- 시각은 모두 `System.nanoTime()` 기준, 예매 출발(`gate.countDown()`) 시점을 0으로 하는 상대 ms다.

## 지표와 판정 (`buildReport`)

- `phantomStockViews = views.count { soldOutAtMs != null && it.sentAtMs > soldOutAtMs && it.remaining > 0 }`
- `staleWindowMs = phantom 조회의 sentAtMs 최댓값 − soldOutAtMs`. phantom이 없으면 0.
- `viewCount = views.size`, `viewDbReads = views.count { it.fromDb }`. 캐시가 DB를 얼마나 막아 주는지가 이 축의 비용 면이다.
- 정합 판정식과 DEGRADED 규칙은 M2 그대로. 위 값들은 판정에 들어가지 않는다.

기대값(N=100, M=1,000, `raceWindowMs=20`, `CONDITIONAL_UPDATE` + `UNIQUE_CONSTRAINT`, 앱 2대):

| cacheConsistency | phantom | staleWindowMs | viewDbReads |
| --- | --- | --- | --- |
| `NONE` | 수백 | 실행 끝 + 꼬리 2초까지 | 1 |
| `TTL_SHORT` | 수십 | ≤ 1,000 | 실행 초 수 + 2 |
| `INVALIDATE_ON_WRITE` | 수백 (경합이 걸린 실행) | 실행 끝까지 | 쓰기 수에 비례 |
| `REDIS_AS_SOT` | 0 \~ 1 | 0 \~ 수 ms | 0 |

`INVALIDATE_ON_WRITE`는 20ms 창에 10ms 폴링이면 거의 매 실행 경합이 걸릴 것으로 보고, 실제 재현율은 DoD 스크립트로 확인한다.

## UI (`static/index.html`)

- `cacheConsistency` 라디오 그룹 4개(NONE 기본). 요청 본문 `strategies.cacheConsistency`. 제목을 M3로.
- `REDIS_AS_SOT`를 고르면 `oversell` 라디오 5개를 `disabled`로 회색 처리한다. 기존 `f.onchange`에 한 줄 추가.
- 그리드 위에 한 줄: `조회자가 보는 잔여석: {lastView} / 실제: {N − ok}`. `lastView`가 -1이면 "-". 매진 뒤에도 왼쪽 숫자가 남아 있는 장면이 이 마일스톤의 설득 장치다.
- 리포트 JSON 아래에 고정 해설 한 블록(DoD 항목). 항상 펼쳐진 상태로, 전략마다 한 줄:
  - NONE: TTL이 끝날 때까지 옛값. 실행이 그보다 짧으면 끝까지 stale.
  - TTL_SHORT: 창이 TTL 이하로 줄지만 닫히지 않는다. 0으로 만드는 TTL은 캐시를 없앤 것과 같다.
  - INVALIDATE_ON_WRITE: 마지막 쓰기의 삭제 뒤에 늦게 온 재적재는 다시 지워지지 않는다.
  - REDIS_AS_SOT: 두 번째 복사본이 없어 0에 가깝다. 그래도 읽은 값은 보는 순간 이미 과거다.

## 인프라

- `build.gradle.kts`: `spring-boot-starter-data-redis` 추가. `StringRedisTemplate`만 쓴다.
- `docker-compose.yml`: `redis` 서비스(`redis:7-alpine`). `app-1`·`app-2`·`web` 모두 `SPRING_DATA_REDIS_HOST=redis`와 `depends_on: redis`.
- `application.yml`: `spring.data.redis.host: ${REDIS_HOST:localhost}`.

## 검증

- `ReportTest`: (1) `soldOutAtMs` 이후 `remaining > 0` 조회만 phantom으로 세고 `staleWindowMs`는 마지막 phantom 시각 차, (2) phantom이 있어도 verdict는 PASS, (3) `soldOutAtMs == null`이면 둘 다 0. 기존 테스트는 기본값으로 그대로 통과한다.
- `scripts/dod.sh`: M3 구간 추가. `CONDITIONAL_UPDATE` + `UNIQUE_CONSTRAINT` + 앱 2대에서 캐시 전략 4종을 각 `RUNS`회. 출력에 `phantom=`, `stale=`, `viewDb=` 컬럼.
- 실행 후 README에 M3 표·로드맵 체크·구조 목록 갱신, `decisions.md`에 결정 행 추가: REDIS_AS_SOT가 oversell 축을 덮음, DB 쓰기 동기, phantom은 판정 제외, 조회자 상수(2개·10ms·꼬리 2초), soldOutAt = N번째 OK 응답 시각, fill 경로에 지연 주입, `staleWindowMs`·`viewDbReads` 추가.
