# M1 설계 — 전략 확장 + 앱 대수 토글 + 성능 지표 + 좌석 그리드

2026-09-20. 상위 스펙: `concurrency-ticketing-lab_spec.md`. M0 설계: `2026-09-20-m0-design.md`. 결정 근거: `docs/decisions.md`.

## 목표

오버셀 전략을 `LOCAL_LOCK`, `PESSIMISTIC`, `OPTIMISTIC`으로 늘리고, 재시도 수·커넥션 피크를 수집하고, DEGRADED 판정을 추가하고, 실행 중 좌석 그리드가 칠해지게 한다.

DoD: `LOCAL_LOCK` + 앱 1대는 PASS, 같은 설정에 앱 2대는 FAIL. 이 대비가 화면에서 한눈에 보일 것.

## 범위 밖

SSE, 라인 차트, `lockWaitMs`, `errorBreakdown`, 빨강 셀(중복 배정, M2), 비교·replay 엔드포인트, seat/reservation 테이블, Redis.

## 전략 구현 (app, `ReservationService`)

지연 주입(`Thread.sleep(raceWindowMs)`)은 세 전략 모두 **읽기와 쓰기 사이**에 둔다. 락을 잡은 채 잠드는 것이 비용의 실체이므로, 그래야 처리량 차이가 드러난다. `CONDITIONAL_UPDATE`는 read-modify-write 창 자체가 없으므로 M0처럼 지연 없음.

| 전략 | 구현 | 기대 결과 |
| --- | --- | --- |
| `LOCAL_LOCK` | `NONE`의 read → sleep → write를 JVM 전역 `synchronized(lock)`으로 감쌈. 트랜잭션 없음. | 앱 1대 PASS, 2대 FAIL |
| `PESSIMISTIC` | `TransactionTemplate` 안에서 `SELECT remaining FROM event WHERE id=? FOR UPDATE` → sleep → `UPDATE event SET remaining = remaining - 1 WHERE id=?`. | PASS. 트랜잭션이 커넥션을 점유하므로 `dbConnectionPeak`가 풀 크기(20)에 붙음. M=5,000이면 Hikari 대기 초과(30초)가 ERROR로 집계 |
| `OPTIMISTIC` | 루프: `SELECT remaining, version` → `remaining<=0`이면 SOLD_OUT → sleep → `UPDATE event SET remaining = remaining - 1, version = version + 1 WHERE id=? AND version=?`. 1행이면 OK, 0행이면 `retries++` 후 반복. | PASS. `retryCount` 폭증 |

락 객체는 이벤트별이 아니라 전역 하나. 실행당 이벤트가 하나이므로 차이가 없다.
`OPTIMISTIC` 재시도 상한 없음. 버전당 정확히 한 요청이 이기므로 진행이 보장되고, 매진 뒤에는 읽기 직후 SOLD_OUT으로 빠진다.

## 성능 지표

`ReserveResponse`에 `retries: Int`, `activeConnections: Int` 추가.

- `retries`: `OPTIMISTIC`의 재시도 횟수. 다른 전략은 0.
- `activeConnections`: `ReserveController`가 `HikariDataSource.hikariPoolMXBean.activeConnections`를 요청 처리 전후로 읽어 큰 값. 앱은 무상태를 유지한다.

web 집계(`buildReport`): `retryCount = Σ retries`, `dbConnectionPeak = max activeConnections`. 인스턴스별 풀이므로 최대값은 "한 앱의 풀이 얼마나 찼는가"를 뜻한다. `Sample`에 두 필드가 추가된다(ERROR 샘플은 0).

## DEGRADED 판정

- `Verdict`에 `DEGRADED` 추가.
- `LoadRunner`가 `(seatCount, userCount, appInstances, raceWindowMs)` 키로 마지막 `NONE` 실행의 처리량을 메모리 맵에 보관. `NONE` 실행이 끝날 때만 갱신.
- `RunReport`에 `baselineThroughput: Double?` 추가. `buildReport(..., baselineThroughput)`.
- 판정: 정합성 위반 → FAIL. 기준선이 있고 `throughput <= 0.5 * baseline` → DEGRADED. 그 외 PASS.

## 진행 상황과 그리드

- `data class Progress(val ok: AtomicInteger, val soldOut: AtomicInteger, val error: AtomicInteger)`. `RunState`에 `progress: Progress` 추가. Jackson은 AtomicInteger를 숫자로 직렬화한다.
- `LoadRunner.run(runId, spec, progress)`가 샘플마다 해당 카운터를 증가.
- UI(`index.html`):
  - 실행 중 200ms 폴링, 종료 후 중단.
  - N칸 그리드. 앞 `min(ok, N)`칸 초록, 나머지 회색. `ok > N`이면 초과분(`ok - N`)을 주황 칸으로 뒤에 붙임.
  - 판정 배지(PASS 초록 / DEGRADED 노랑 / FAIL 빨강)를 크게. 그 아래 리포트 JSON은 지금처럼 그대로.
  - 전략 라디오에 세 전략 추가. `LOCAL_LOCK` + 앱 2대이면 앱 대수 select를 하이라이트.
- `POST /api/runs` 응답, 409 처리, 폼 잠금은 M0 그대로.

## 검증

- `ReportTest`: retry 합·커넥션 최대·DEGRADED(기준선 있음/없음) 케이스 추가. 기존 4개 유지.
- `scripts/dod.sh`를 M1 DoD로 교체: 전략 5종 × 앱 1대/2대를 각 3회 실행하고 `verdict oversold ledger errors rps p99 retries connPeak`를 한 줄로 출력. 기대: `LOCAL_LOCK`은 1대 PASS·2대 FAIL, `CONDITIONAL_UPDATE`·`PESSIMISTIC`·`OPTIMISTIC`은 양쪽 모두 PASS(또는 DEGRADED), `NONE`은 양쪽 모두 FAIL.
